## Java Backend Errors

### 1. `src/model/UserProfile.java:11` — Compilation Error

**Problem:** The two-argument constructor names its parameter `profileId` (lowercase `d`), but line 11 calls `setProfileID(profileID)` (uppercase `D`). `profileID` is not defined in this scope, so the file **will not compile**.

```java
// BROKEN (line 10–12)
public UserProfile(int profileId, int sessionID) {
    setProfileID(profileID);   // ❌ profileID doesn't exist
    setSessionID(sessionID);
}

// FIXED
public UserProfile(int profileId, int sessionID) {
    setProfileID(profileId);   // ✅ matches the parameter name
    setSessionID(sessionID);
}
```

### 2. `src/model/Outfit.java:10` — Logic Bug (silent wrong value)

**Problem:** The one-argument constructor names its parameter `OutfitID` (uppercase `O`), but line 10 calls `setOutfitID(outfitID)` (lowercase `o`). In Java, `outfitID` resolves to the **instance field** (default value `0`) instead of the passed-in parameter. The constructor silently does nothing useful.

```java
// BROKEN (line 9–11)
public Outfit(int OutfitID) {
    setOutfitID(outfitID);   // ❌ passes the field (0), not the parameter
}

// FIXED
public Outfit(int OutfitID) {
    setOutfitID(OutfitID);   // ✅ passes the parameter
}
```

### 6. `frontend/src/components/ui/HeaderBar.jsx:1,9,10` — Unused Import + Unused Params

### 7. `frontend/src/features/outfit-curator/OutfitBuilderPage.jsx:94–96` — useEffect Missing Dependency

**Problem:** `fetchAllItems` is defined outside the `useEffect` but called inside it. ESLint's `react-hooks/exhaustive-deps` rule flags this because `fetchAllItems` is a new function reference every render. The simplest fix is to move the function body inside the effect.

```jsx
// BROKEN
async function fetchAllItems() {  // defined outside — new ref every render
  ...
}
useEffect(() => {
  fetchAllItems();            // ❌ missing dep warning
}, [occasion, gender]);

// FIXED — move function body inside the effect
useEffect(() => {
  async function fetchAllItems() {
    try {
      const params = new URLSearchParams();
      if (occasion) params.append("occasion", occasion);
      if (gender)   params.append("gender",   gender);
      const res  = await fetch(`http://localhost:8080/api/items?${params.toString()}`);
      const data = await res.json();
      setAllItems(data);
    } catch (error) {
      console.error("Failed to fetch items:", error);
    }
  }
  fetchAllItems();
}, [occasion, gender]);        // ✅ no missing dep — occasion & gender are stable search params
```

## Routing Bug

### 11. `frontend/src/features/receipt/ReceiptPage.jsx:22` — "← Edit Outfit" loses query params

**Problem:** The GoBackButton in ReceiptPage navigates to `/builder` with a hardcoded `destination` prop. The builder page reads `?occasion=X&gender=Y` from the URL via `useSearchParams()`. Navigating to bare `/builder` gives it no params, so it re-renders with `occasion = null` and `gender = null`, firing an API call with no filters and losing the outfit the user built.

```jsx
// BROKEN — navigates to /builder with no query params
<GoBackButton destination="/builder">
  ← Edit Outfit
</GoBackButton>

// FIXED — remove destination prop so GoBackButton falls back to navigate(-1),
// which goes back in browser history and preserves the correct /builder?occasion=X&gender=Y URL
<GoBackButton>
  ← Edit Outfit
</GoBackButton>
```

**Note:** `navigate(-1)` goes back one step in browser history. Since the user arrived at `/receipt` from `/builder?occasion=X&gender=Y`, pressing back will correctly restore the builder URL. The builder's `selectedItems` state will be reset (it lives in component memory), but at least the filters and API call will be correct. Persisting `selectedItems` across back-navigation would require storing it in `location.state` or `sessionStorage`.
